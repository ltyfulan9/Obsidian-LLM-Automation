# 产品定义与交付标准

## 要解决的问题

个人笔记、AI 对话、计划和执行结果散落在不同文件里。仅把文件备份到 Git，既不能回答“这个判断从哪里来”，也不能回答“我后来做成了吗”。

本项目帮助一个人把**明确选择的本机资料**变成可追溯、可查找、可回顾的知识库，再把本人确认的行动与实际结果连接起来。主要使用方式是 CLI 自动处理、Obsidian 阅读和手写补充；公共工具与真实知识工作区分开。

## 核心用户旅程

```mermaid
flowchart LR
    A[用虚构资料试用] --> B[检查本机是否就绪]
    B --> C[明确选择自己的来源]
    C --> D[增量整理]
    D --> E[从日期或主题查回证据]
    E --> F[本人确认行动并回填结果]
    F --> G[依据记录复盘]
    G --> D
```

用户每次都应该能知道：工具读了什么、用了哪种整理方式、哪些结果已保存、是否发送到网络，以及下一步该做什么。

| 用户要做的事 | 产品应提供的结果 | 不应让用户猜什么 |
| --- | --- | --- |
| 判断是否适合自己 | 不使用真实内容的离线演示 | 是否必须配置模型或 GitHub 才能试用 |
| 配置并开始导入 | 明确来源、诊断结果与可执行的修复步骤 | 文件没变与采集失败是否相同 |
| 找回过去的知识 | 主题/日期导航、出处与整理方式 | 搜到的是原文、摘录、AI 观点还是本人承诺 |
| 每天维护 | 增量处理、清楚的成功点与失败状态 | 上一次成功是否能证明这一次成功 |
| 长期保存 | 可验证的状态备份与新目录恢复流程 | Git 上的 Markdown 是否等于完整运行状态 |
| 检查自己的行动 | 预计与实际结果、带日期的变更与依据 | AI 的建议是否已经算成本人承诺 |

## 内容与信任约定

- `extract` 是本地摘录和有限关键词分类，页面必须明确标注；不能把它描述成模型理解。
- AI 摘要仍需核对来源。作者主张、计划与实际结果分开，不能自动补齐缺失事实。
- 未记录的日期是未知；复盘发现是需要核对的具体事件，不是人格评价。
- 添加来源是用户的选择，不自动扫描所有磁盘或登录账户。真实内容不放入公共示例。
- 普通同步更新本地。模型处理、GitHub 发布和 Magpie 同步是不同的数据流，应各自说明和验证。
- 调度配置生成、系统已注册、某次执行成功是三个不同状态，不混为“已自动化”。

## 三轮交付门槛

下面是工作门槛，不是对全部功能已经完成的宣称。各轮实际结果以[验证记录](validation.md)及对应提交为准。

| 轮次 | 解决的用户阻碍 | 必须通过的验收 |
| --- | --- | --- |
| 第一轮：首次使用可验证 | 新用户还未准备私人资料，就得理解全部设置 | 新空目录下离线演示完成两份虚构资料、导航、承诺和每日回填；无需模型/网络；重复目录不覆盖；诊断区分健康与阻碍并给出下一步 |
| 第二轮：日常知识可使用 | 来源、主题与手写内容之间难以往返，搜索结果难以判断 | 中文、空格、相对链接的合成资料能完成查找与证据回溯；首页有清楚的阅读入口；搜索显示命中依据并保留摘录/AI/本人记录的区别 |
| 第三轮：长期运行可托付 | 故障和迁移时只能手工猜测如何恢复 | 最近尝试与最近成功可区分；一致性状态备份可在新目录恢复；回填、承诺、事件及增量状态可验证一致；拒绝覆盖现有工作区；中断场景可恢复 |

每轮包含具体修改、跨角色评审和一次真实 CLI 用户旅程。不能用三次文案润色代替三轮，也不能把模拟测试说成真实模型调用或真实系统任务执行。行为变化后运行全套测试，最终提交需要 Windows、macOS、Linux 的跨平台 CI。

## 这阶段不做什么

不扩展为全网资讯服务、交易机器人、私人社群抓取器或心理诊断工具。也不为架构外观先引入向量数据库、分布式队列或多 Agent 运行平台。先修复当前用户旅程中的明确断点，再根据真实使用证据选择后续能力。

默认维持本地文件、标准库核心和可阅读的 Markdown 产物。模型和私有发布都是可选能力；工具应该在没有它们的情况下也能完成真实、有边界的工作。
